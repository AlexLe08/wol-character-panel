# 0004: 2.0 ships as betas on `next`

Status: Accepted · 2026-11-13

## Context

2.0's changes merged on `main` over #24 to #30 (2026-11-12 and 13): `CharacterWindow`,
the gear-set row, and the breaks that ride along (`CharacterSheet` renamed
`EquipmentPanel`, `parts` replacing the `show*` props, `tab` and `page`
reserved, tighter limits). None of it has been used by a host yet; the
site, the only host, is on 1.x.

npm installs the `latest` dist-tag by default, and `npm publish` moves
`latest` to whatever it publishes. npm 11 refuses to publish a prerelease
version without `--tag`. #31 (`ba7aea8`, `ceb85ae`, `87ad129`) made
`release.yml` publish a version containing `-` with `--tag next`, made the
Demo deploy skip prerelease tags, and made `/release-prep` propose
`2.0.0-beta.N` until the owner says the API is settled.

## Decision

2.0 is released as `2.0.0-beta.N` on npm's `next` tag while `latest` stays
on 1.0.4. The site upgrades to `@next`, and what it runs into goes in the
roadmap as the beta's findings. 2.0.0 is released once a beta has gone
about a week without an API change.

## Consequences

- `npm install @solution-nine/wol-character-panel` keeps giving 1.0.4;
  only a host asking for `@next` (or an exact beta) gets 2.0.
- The API can still change between betas, each one a new `beta.N`, without
  a 3.0. A range like `^2.0.0-beta.0` also takes later betas, and 2.0.0,
  so a host on a beta range picks up those changes on its next install.
- The public demo shows 1.0.4 until 2.0.0, so 2.0 is seen in the
  playground or in the site, not on GitHub Pages.
- The schema's `$id` reads `@2` from the first beta, since it's built from
  the major, so the betas already name the 2.x contract.
- 1.x has no branch of its own; a 1.x fix would need `release/1.x`
  ([0005](0005-small-prs-squash-only.md)).
- The release date depends on the site's upgrade and a quiet week, not a
  fixed date.
